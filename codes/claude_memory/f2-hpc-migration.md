**FRAMEWORK CHOICE FOR THE PLANT PORT (analysis 2026-09-14 — do NOT default to JAX):** the deciding factor is that the whole learner (actor, critic, PPO, F1 distilled net) is ALREADY PyTorch, and PPO is MODEL-FREE so it needs NO gradients through the dynamics (differentiable-sim = irrelevant here, removes JAX's main selling point). Options: (1) **JAX** (Brax/MJX style: vmap over envs + lax.scan over time + jit -> best-in-class XLA fusion, kills the launch-bound risk) BUT functional paradigm + you'd have to port the ENTIRE RL loop to JAX to stay on-device (PureJaxRL-style) = whole-pipeline rewrite, not plant-only. (2) **PyTorch + torch.compile + CUDA graphs** -> reuse everything, one framework, zero bridge; but you manage fusion/launch discipline manually (CUDA graphs to capture the 3100-step loop). (3) **NVIDIA Warp (physics) + PyTorch (learner)** = PREFERRED: Warp compiles explicitly-FUSED CUDA kernels (best launch discipline, purpose-built for ODE physics) AND interops with torch tensors on-GPU, so the existing PPO/nets stay unchanged and you port ONLY the plant (matches the plant-port-only scope). RECOMMENDATION: Warp+torch first; pure-torch (compile+CUDA graphs) as the zero-new-dependency fallback; JAX only if willing to rewrite the full loop for cleanest end-to-end jit. The #1 risk in ALL of them is the same: the integrator MUST be fused (few kernels/step) or it goes launch-bound over 3100 steps -> 3-5x instead of ~50x.
