**THE ISSUE (named from code, [_build_obs residual_marl_env.py:462-490]).** The 80-D per-agent obs = load18[p,R,v,w] + own[dpos,dvel] + f_g + f_lam + clk(14) + d1/d2 (delta frames, 18 each) + ref18[pd,Rd,vd,wd]. THREE position triples are ABSOLUTE world coords: load pos **p**, own drone pos **dpos**, desired load pos **pd** — all grow linearly with displacement. Velocities (v, vd, dvel) grow with SPEED. Rest (R, w, forces, clock, deltas) bounded/scale-invariant. => the net learns a function of WHERE IT IS in the world, which is suspected to foreclose scale generalization.

**WHY absolute-pos is suspected to foreclose scale-gen (3 stacked reasons):** (1) NOT translation- or scale-invariant — a 25m move visits absolute coords the 5m-era training never touched; mapping undefined there. (2) MLPs DON'T EXTRAPOLATE — even with a perfect norm, feeding pd=25m to a net trained on pd∈small range is far outside the training manifold = unfit-region output (the DEEPER reason, independent of norm). (3) FROZEN NORM compounds — warm-start reuses the checkpoint's obs_mean/std (set once at [mappo.py:498], NEVER updated in the loop), so at large displacement both p and pd get ÷ a smaller-scale std -> saturate -> the physically-relevant SMALL quantity (error p-pd) is lost as the difference of two large saturated numbers.

**CONSTRAINTS any future fix must respect (raised by user in discussion — record so we don't re-propose broken versions):**
- **No drone reference exists.** The carriers loiter/orbit to hold the load; there is NO desired drone position. So any "drone tracking error" vs a drone target is bogus — there is no such target.
- **Don't corrupt clean own-state with the noisy load.** `dpos` is (near-)clean proprioception; the LOAD is a NOISY, DELAYED estimate. Subtracting the measured load from the drone position would INJECT load-estimate noise into a clean signal. (The clean reference pd, by contrast, is analytic/deterministic.)
- **"The net can compute p−pd internally, it already has p, pd, dpos."** TRUE, and a real objection to any error-feature proposal. Counter-consideration (not yet agreed as decisive): it's about INPUT RANGE not information — an MLP generalizes only over its trained input distribution and doesn't extrapolate; to subtract internally it must first receive the large OOD operands, which may already saturate the first layer before the difference forms. Feeding a difference directly would add no info but keep that input ~constant-magnitude across scales. OPEN whether this actually buys generalization here or not.
- **No-comms (thesis).** Any obs change must stay own drone state + own load estimate + own mission reference (pd from own clock) — NOT relative to OTHER drones (that IS the ruled-out communication, [[f2-residual-rl-plan]]).

**SCOPE — even if an obs change helped, it addresses only ONE of the >=2 scale failure axes ([[f2-speed-binding-axis]]):** at most DISPLACEMENT/translation (Case C's distance part). NOT speed (velocities scale with v_peak AND speed changes the physics — load equilibrium tilts back, P14/P15) and NOT duration (long-episode drift-to-cliff = the coordination-leak wall, F_null, [[f2-wd-nullleak-breakthrough]]).

**COST / FRAMING for the design session:** any obs change alters obs_dim -> warm-start INCOMPATIBLE -> FROM-SCRATCH retrain (not a patch like re-norm/laddering). The REWARD has a parallel absolute-coordinate term (`d2 = ||expert_pos[i][idx] − p_i||²` uses ABSOLUTE expert_pos) — revisit alongside. The genuine choice to weigh: ABSOLUTE obs works WITHIN whatever range you train on (reachable via ladder/curriculum) but not zero-shot beyond it; a scale-invariant obs would be the path to transfer to UNSEEN scales — but its value depends on whether the thesis needs a bounded operating envelope vs genuine scale-INVARIANCE as a contribution.
