## The optimizer-in-the-reward idea — careful

I think you're conflating two roles the optimizer can play, and the distinction matters:

- **In-the-loop:** the optimizer's `λ` physically produces `fλ = N·λ`, which actually drives the cables. This is what makes F2 "residual *on top of* the optimizer." The optimizer is doing the real work; RL only corrects.

Your proposal ("run optimizer separately, inject its output into the reward, decay the weight toward pure tracking") is the **second** one. - If the optimizer is *also* driving (in-loop) during this phase, then the agent's residual is being trained to match a target while never actually being in control. When you finally remove the optimizer, the states drift off the distribution the agent ever saw → classic **behavior-cloning distribution shift**, and the "smooth handoff" isn't smooth.
- If the optimizer is *not* driving and only the agent acts, then early on the agent is garbage, the drones stall/desync, load tracking blows up, and your "imitate the optimizer" reward is being computed on states the optimizer would never have visited. The imitation signal is off-distribution and misleading.

The reason residual RL (F2 done properly) sidesteps all this: **the agent's action is always applied to the plant**, so it always sees the consequences of its own actions. That's what makes the eventual handoff honest.

## `step` (lines 159–189)


## What PettingZoo is

PettingZoo is to **multi-agent** RL what Gymnasium is to **single-agent** RL. Gymnasium's `Env` assumes *one* agent: one observation in, one action out, one reward. But we have 4 drones, each with its own observation, its own action (`δf_i`), and its own reward. PettingZoo defines the standard API for exactly that — same maintainers as Gymnasium, so it's the de-facto interface every MARL library (MAPPO implementations, RLlib, etc.) already speaks.

It's a **contract/interface**, not an algorithm. It doesn't train anything. It just standardizes how a multi-agent environment talks to a multi-agent trainer, so you can swap trainers without rewriting the env.

## The one API we'd use: `ParallelEnv`

PettingZoo has two flavors. **AEC** (agents act one-at-a-time, turn-based — think chess). **Parallel** (all agents act *simultaneously* each step — think our drones, all applying forces at the same instant). We want **Parallel**.

A `ParallelEnv` looks almost like Gymnasium, except everything per-agent becomes a **dict keyed by agent name**:

```python
agents = ["drone_0", "drone_1", "drone_2", "drone_3"]

obs, info = env.reset()
#   obs = {"drone_0": <24-vector>, "drone_1": <24-vector>, ...}

actions = {"drone_0": δf_0, "drone_1": δf_1, ...}   # each ℝ³
obs, rewards, terminations, truncations, infos = env.step(actions)
#   rewards = {"drone_0": r0, "drone_1": r1, ...}
#   each of these is a dict, one entry per agent
```

Plus two space accessors (per-agent, since agents could in principle differ):
```python
env.observation_space("drone_0")   # Box(24,)
env.action_space("drone_0")        # Box(3,)  -> δf
```

## The one extra piece for our CTDE setup

Our plan is **Centralized Training, Decentralized Execution** (MAPPO): each actor sees only its **local 24-D obs**, but the **critic** during training sees the **global state** (all drones + true load). PettingZoo's Parallel API adds exactly one method for this:

```python
env.state()   # the full global state vector, for the centralized critic only
```

So the actors read the per-agent `obs` dict (local, decentralized — deployable on real drones), and the critic reads `state()` (global, training-only, thrown away at deployment). That split is the whole point of CTDE, and PettingZoo bakes it in.

## Delay vs clock offset — the conceptual difference

They both make an expert act on "wrong" information, but in orthogonal ways:

**Delay = right value, old timestamp.** The expert sees the *true* load state, but from *d* steps in the past. The load really *was* there; the information just arrived late. This models **sensor / communication / processing latency** — the classic decentralization killer.
> *Analogy:* four people reaching for a moving ball, each looking at a photo taken a fraction of a second ago. The photo is accurate; it's just stale.

**Clock offset = the agent's sense of *time* is wrong.** The expert isn't seeing old data — it evaluates every **time-dependent** quantity at a shifted `t`. Two consequences, both from `t_i = t + offset`:
- Its **reference trajectory** `get_reference_trajectory(t_i)` is evaluated at the wrong time → it thinks the load is *supposed* to be somewhere slightly different right now.
- Its **internal-force sinusoid** `λ(t_i) = A·cos(ξ·t_i + φ)` is phase-shifted → its oscillation drifts out of sync with the others.

This models **unsynchronized clocks** between drones — they don't agree on "what time it is," so their desired poses and their oscillation phases diverge.
> *Analogy:* four people whose watches read different times, each reaching for where the plan says the ball *should* be *now* — but "now" differs for each of them.

Why both cause desync in the stitch: each expert's slice is computed under a different assumption (stale state, or shifted time), so the four slices no longer combine into one coherent wrench. The load feels an inconsistent force set → tracking degrades → the residual has a real job.

## The "update-rate skew / internal-`dt`" issue

**Update-rate skew** = experts recomputing at *different rates*. E.g. drone 0 recomputes its force every step (100 Hz) but drone 2 only every 3rd step, holding its last force in between (a slower control loop, or dropped commands). Another realistic desync.

**Why it's fiddly:** inside `ClassicalAgent.optimize`, several quantities are computed by **finite differences that divide by `self.dt` (=0.01)**:
```python
G_pinv_dot = (G_pinv - self.prev_G_pinv) / self.dt
w_d_dot    = (w_d   - self.prev_w_d)    / self.dt
N_dot      = (N     - self.prev_N)      / self.dt
```
These assume the previous value was from *exactly one* `dt` ago. If an expert skips 2 steps and recomputes on the 3rd, then **3·dt of real time actually elapsed**, but the code still divides by `dt` → it overestimates every derivative by 3×. Those wrong derivatives feed the optimizer's constraint (the `e` term, eq. 20), so the sinusoid parameters go haywire.

To do it correctly I'd have to thread a per-agent "time since my last recompute" into `optimize` and divide by *that* instead of the fixed `self.dt`. Totally doable, but it means changing `ClassicalAgent`'s internals (and being careful the analytic sinusoid derivatives, which use the true `t`, stay consistent). That's more than a wrapper-level tweak, so I parked it. Delay + clock offset give us solid temporal desync without touching the expert's guts.

## What "MAPPO from scratch" actually is

MAPPO = **PPO** with a **centralized critic**. If you understand single-agent PPO, you understand 90% of this; the multi-agent part is small. Four pieces:

**1. Actor `π_θ(a_i | o_i)`** — one shared network.
- Input: a drone's local obs (24). Output: the **mean** of a 3-D Gaussian over `δf`, plus a learnable log-std. Sample → action, clipped to [-1,1].
- Shared across all 4 drones (parameter sharing): same weights, four different inputs.

**2. Critic `V_φ(state)`** — one shared centralized network.
- Input: the **global** state (42, from `env.state()`). Output: one scalar value.
- This is the CTDE part — it sees everything during training, and is thrown away at deployment.

**3. Rollout buffer + GAE** — collect `T` steps of `(o_i, a_i, logp_i, r_i, done)` per agent and `(state, V)` per step; compute advantages with Generalized Advantage Estimation, per agent (each uses its own reward stream against the shared `V`).

**4. PPO update** — the clipped surrogate loss for the actor, MSE for the critic, an entropy bonus; a few epochs of minibatch SGD over the collected batch. All 4 agents' experience pools into the one shared actor update.

**Training loop:** `collect rollout → compute GAE → PPO update → repeat`.

ASSISTANT:
It's a way to **stop the RL policy from wandering off into nonsense** by tethering it to the imitation-learned policy. Two flavors of the same idea:

## BC = Behavior Cloning regularizer
Add a **supervised term** to the RL loss that keeps pulling the policy toward the *expert's* action:
```
loss = RL_loss  +  λ_bc · ‖ π_θ(o) − a_expert ‖²
```
"Do whatever RL wants, **but also keep matching the expert** on these states." Needs the **expert action labels** (from your IL dataset, or by querying the optimizer). It's literally "keep doing a bit of imitation learning during RL."

## KL regularizer
Freeze a copy of the IL-trained policy as a **reference** `π_ref`, and penalize the current policy for drifting away from it in distribution:
```
loss = RL_loss  +  β · KL( π_θ(·|o) ‖ π_ref(·|o) )
```
KL (Kullback–Leibler divergence) measures how different two probability distributions are. This says "the new policy's action distribution must stay **close to the reference's**, unless the reward *really* justifies moving." Needs only the **frozen reference network**, not expert labels at RL time. (This is exactly the trick RLHF uses to keep a fine-tuned LLM near its base model.)

## Why it fixes your two fears
- **Reward hacking / vibration:** the IL policy imitates the smooth optimizer — it *doesn't* vibrate. Any vibrate-in-place exploit is *far* from `π_ref`, so it incurs a big KL (or BC) penalty. RL would have to overcome that penalty to adopt the exploit — which it won't, for a degenerate solution. The anchor makes the sane region the path of least resistance.
- **Catastrophic forgetting:** the policy can't silently forget the hover/track/non-stop base skill, because straying from `π_ref` is directly penalized.

## How we'd use it
1. IL-train the policy → save a frozen copy as `π_ref`.
2. RL fine-tune with `β·KL(π_θ‖π_ref)` (or a BC term) added to the loss.
3. **Anneal `β` down** over training — start tightly anchored (trust the expert), gradually loosen as RL proves it can do better. High `β` = "barely move from imitation," low `β` = "mostly trust RL."

Practical notes: **KL is usually preferred** because it only needs the frozen reference (no expert labels during RL) and it's distribution-aware. **BC** is simpler and sometimes more stable but needs the action labels. You can even use both. It's one scalar knob (`β` or `λ_bc`) plus one frozen network — cheap insurance against exactly the degeneracy you're worried about.

## The core difference: IL has a label, RL doesn't

**In IL**, every sample comes with the **correct answer** — the expert's action. Training is just "make your output match the label." Each `(obs, expert_action)` is self-contained; you never need to know what happened *next*. So you can shuffle all 10,000 rows immediately and train.

**In RL**, there's **no correct-action label.** The policy tried *some* action, and you need to figure out: *was that a good action or a bad one?* Nobody tells you. The only way to find out is to **see how things turned out afterward** — i.e., look at the rewards that came *after* that action.

## Why that forces temporal, per-agent processing

To grade the action drone 0 took at `t=100`, you need the rewards drone 0 received at `t=100, 101, 102, …` — because an action's quality depends on its future consequences, not just the immediate reward. That "how did it turn out" number is the **return**, and the **advantage** ≈ "how much better did it turn out than the critic expected."

Computing that **requires the rewards in time order, kept separate per agent.** If you shuffled all 10,000 rows *first*, you'd destroy "which reward follows which, for which drone," and you couldn't compute it.

**Analogy:** grading chess moves.
- *IL:* a grandmaster labels each position with the best move. You compare your move to the label. No need to watch the rest of the game.
- *RL:* nobody labels the best move. To know if your move at turn 20 was good, you have to **watch the rest of the game** (turns 21, 22, …) and see if you won. And you grade *each player's* moves along *their own* game.

## So the two-step workflow (RL only)

1. **Roll out** → for each agent, an ordered-in-time sequence: `obs_t, action_t, reward_t, value_t`.
2. **Grade (per agent, in time order):** walk each agent's trajectory to compute `advantage_t` from its future rewards. ← *this* step needs the temporal order and per-agent grouping.
3. **Now flatten:** every `(obs, action, advantage)` becomes an independent row. Pile all agents × all timesteps into 10,000 rows.
4. **Shuffle & train** (PPO update). Order and agent identity no longer matter here.

**IL skips steps 1–2 entirely** — it already has the labels, so it jumps straight to "10,000 independent rows, shuffle, train."

## Walkthrough — `networks.py` (your points 3 & 4)

**Point 4 first — "Gaussian policy" / `distribution`:** A deterministic policy outputs one action `a = f(obs)`. A **stochastic (Gaussian) policy** instead outputs a *probability distribution* over actions — here a Normal (bell curve) with a mean `μ(obs)` from the network and a spread `σ`. To act, you **sample** `a ~ Normal(μ, σ)`. Why bother? **RL needs randomness to explore** (try actions near the mean, see which are better), and PPO's math needs the **probability** of the action taken (`log_prob`) to compute its update. So:
- `forward(obs)` → **μ** (the mean). For **IL** we only want the mean — regress `μ → λ` — so IL ignores σ entirely and it's just plain regression.
- `distribution(obs)` → `Normal(μ, σ)`, the object PPO samples from and asks for `log_prob`/entropy. `σ = exp(log_std)` where `log_std` is a learned parameter (exp keeps σ positive). It's **state-independent** (one σ for all states) — the standard, stable default for continuous PPO.

Building it this way means **one network serves both phases**: IL trains the mean, RL later reuses the exact same weights and just starts sampling.

**Point 3 — the MLP architecture, which you're right we never discussed:**
```
obs(24) → Linear(24,128) → tanh → Linear(128,128) → tanh → Linear(128, act_dim)   + log_std param
```
The choices and *why* (all defaults, all changeable — tell me if you'd pick differently):
- **2 hidden layers, width 128:** small-but-ample for a 24-D input. This is a deliberately *over*-capacity choice **for the diagnostic** — I want "can't fit" to mean "impossible," not "too small." For the final policy we might shrink it (your slides cite a tiny net for <<1 ms inference).
- **tanh activations:** the common default for control/PPO policies (smooth, bounded, plays well with normalized inputs). ReLU also fine; tanh is the MAPPO/PPO convention.
- **Linear output (no squashing):** λ is unbounded-ish (±1.5), so a linear head regresses it directly. (For a bounded action like δf we'd add a `tanh` and scale — but λ we leave linear.)
- **Input standardization** (in the trainer, not the net): obs channels have wildly different scales (x-position ~0–11 m vs rotation entries ~±1), so we normalize each channel to mean 0/std 1 before the net. Standard, and it matters a lot for training speed.

## Homogeneity — you just answered your own worry, and it's a good answer

The worry: each drone has a **different constant phase** `φᵢ` (`[0, π/2, 0, π/2]`) and a **different attachment point** `bᵢ`. If two drones at the "same" state need *different* λ, then a single shared network can't serve all four → parameter sharing (homogeneity) breaks.

Your escape hatch — "different relative position to the load" — is exactly right, and here's the mechanism:

- We argued the phase is encoded in the **drone's orbital position**. But that position is measured **relative to the drone's own nominal point** `pL + R·bᵢ`, which differs per drone because `bᵢ` differs.
- So both sources of heterogeneity — the constant `φᵢ` **and** the attachment corner `bᵢ` — show up as **different observable relative positions** `drone_pos − pL`. Drone 0 (corner `b₀`, phase 0) and drone 1 (corner `b₁`, phase π/2) are simply *at different places* in the observation.
- Therefore the shared function the network learns isn't "which drone am I?" — it's **"given where I am relative to the load and how I'm moving, output the λ that continues my orbit."** That single function is the **same for all four drones**, because the per-drone differences are already baked into each one's observed relative position. Homogeneity is preserved *because* the heterogeneity is observable.

The condition for this to hold: two drones that happened to be at the *identical relative position and velocity* should want the *identical* λ. By the limit-cycle argument (same cable length, same local orbit dynamics), they would. So the shared map is well-defined.

**The elegant part:** this means the **same IL experiment tests *both* questions at once.** We pool all 4 drones' data and fit one network. If train MSE → low, then a single function predicts every drone's λ across all phases and corners → *both* "phase is observable" *and* "drones are homogeneous" hold. If it floors high, one of them failed — and we diagnose by **adding a one-hot agent-id to the observation**: if the MSE then drops, it was a homogeneity problem (add the id, done); if it stays high, it's the deeper phase-observability problem. So we get a clean, decisive readout.
